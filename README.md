# cloud-itonami-isic-900: Creative Arts & Entertainment Venue Operations Coordination

An LLM/actor framework for performing-arts venue and production company back-office administrative coordination.

**ISIC Classification**: Rev.4 Division 90 (Creative, arts and entertainment activities)

## What This Does

This actor coordinates the operational infrastructure of performing-arts venues and production companies:

- Venue and rehearsal-space booking scheduling
- Administrative performer schedule coordination (call times, rehearsal logistics)
- Non-creative consumables supply coordination (front-of-house supplies, office supplies, cleaning)
- Box-office and ticketing operational logistics
- Facility and crowd-safety concern flagging

## What This Does NOT Do

This actor explicitly does **not** handle:

- Artistic decisions or creative direction
- Casting or talent selection
- Programming or curatorial choices
- Ticket pricing or revenue policy
- Safety-authority overrides or mandatory reporting (escalates instead)

## Architecture

**Namespace**: `venueadminops`

**Modules**:
- `store` — String-keyed venue/booking directory (MemStore, EDN-backed)
- `advisor` — Proposal generation and rationale (LLM seam)
- `governor` — Three HARD checks (venue verification, effect validation, scope exclusion)
- `phase` — Rollout phases 0–3 (read-only → auto-commit with escalation)
- `operation` — `langgraph-clj` StateGraph: intake → advise → govern → decide → commit | hold | request-approval
- `sim` — Demo driver

**All modules are `.cljc`** (ClojureScript + JVM compatible).

## Governor: Three HARD Checks

1. **Venue unverified**: Target venue/booking must exist AND be `:registered?`/`:verified?` in store.
2. **Effect not :propose**: Any `:effect` other than `:propose` is rejected outright.
3. **Scope exclusion**: Any proposal touching creative/artistic decisions, casting, programming, pricing, or safety-authority territory is permanently blocked.

These are un-overridable, even with human approval.

## Operations (Closed Allowlist)

- `:schedule-venue-booking`
- `:coordinate-performer-schedule-proposal`
- `:coordinate-supply-request`
- `:coordinate-ticketing-logistics`
- `:flag-safety-concern` (always escalates)

## Running

### Tests

```bash
kbb -M:test
```

### Linting

```bash
kbb -M:lint
```

### Demo/Simulator

```bash
kbb -M:run
```

This runs `venueadminops.sim/demo`, which exercises the full operation flow
including all four hard-check failure modes and the escalation rules.

### Operator console (generated by running the actor)

```bash
kbb -M:dev:render-html            # -> docs/samples/operator-console.html
```

`venueadminops.render-html` regenerates
[`docs/samples/operator-console.html`](docs/samples/operator-console.html) by
running `operation/run-operation` 18 times against one fresh
`store/seed-db`. Every venue, booking, event name, date and capacity on the
page is read back out of that store, and every disposition, rule and detail
string is the governor's own output — nothing on the page is hand-written
markup.

The build is a gate, not a report: `-main` **throws** if the run produces zero
HARD governor holds, if the ledger comes back empty, or if any scenario's
declared expectation drifts from what the pipeline actually did. The page is
byte-identical across reruns (`:operation-id` and `:timestamp` are disclosed
in the retention table rather than silently dropped, because a random UUID and
a wall clock cannot be deterministic).

> **Known drift**: the Architecture section above calls `operation` a
> `langgraph-clj` StateGraph. It is not — this repo has no langgraph
> dependency and `run-operation` is a plain `->` threading pipeline, as
> `operation.cljc`'s own docstring records. There is therefore no
> `interrupt-before` resume seam: a `:hold` is terminal and no approver is
> ever recorded. The generated console measures and states this rather than
> implying an approval step exists.
